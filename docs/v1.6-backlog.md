# v1.6 backlog — 2026-08-12 全体レビューからの修正計画

v1.5.1時点の全コードレビュー（全モジュールの構造把握、主要パスの精読、同梱YAML
46本の実`validate`、CI/配布/skills/examplesの点検）から出た修正候補の記録。
このファイルは次の実装セッションの入力であり、実装が終わった項目は
CHANGELOGへ移して削る。`docs/v1-backlog.md` と同じ役割のv1.6版。

判断の前提: 致命的な設計欠陥は見つかっていない。問題は「sfhと外の世界の境界の
運用コスト」と「実戦検証の不足」に集中しており、以下はその手当てである。

## A. エンジン修正

### A1. `require_version:` — 検証済みCLIバージョンの表明と起動時照合

- **問題。** バージョンの床は `agy` の `minimum_version: 1.1.8` 1件だけで、
  それも `preflight` の表示止まり（`src/preflight.rs`）。実行closureの
  バージョン検査は **resume時のみ** 働き、fresh runは無検査で始まる。
  CLIは自動更新するので、flow作者が検証した版と実際に走る版のずれは
  run途中の `SFH_PROTOCOL_INVALID` として最悪の時点で現れる。
- **提案。** flow `defaults` / `profiles.<name>` / step に `require_version:`
  （完全一致または範囲）を追加。起動時に `preflight` の既存プローブ
  （`probe_version_isolated`、副作用防止付き）で照合し、不一致は
  **何もspawnする前に** 拒否する。`--json` は安定コードで応答
  （`SFH_CAPABILITY_UNAVAILABLE` の再利用か新コードかは実装時に判断）。
  `preflight` / `plan` にも宣言と実測の対比を表示する。
- **受け入れ基準。** 不一致でexit 2・spawnゼロ・機械エンベロープあり。
  宣言なしのflowは挙動不変。回帰テスト（一致・不一致・プローブ不能）。

### A2. `when_protocol_is:` — プロトコル状態をrouteから分岐可能に

- **問題。** アダプタドリフトでプロトコルが崩れたstepの生出力は
  `<step>.out.txt` に残り、`outputs` にも警告バナー付きで入る
  （`failed_output`, `src/engine.rs`）ので救済は原理的に可能だが、
  routeは `ProtocolState`（`src/protocol.rs`）を見られない。そのため
  「ドリフト（護送して再解釈）」と「エージェントの本当の失敗（fixループへ）」
  を書き分けられず、fail-closedの実務コストが「払った仕事の再購入」になる。
- **提案。** `Route` に `when_protocol_is: plain|valid|missing_terminal|invalid`
  を追加。既存の `when_*` と同じ合成規則・validate検査に従う。既定挙動は
  不変（書かなければ今まで通り失敗）。`guide` と skills に救済パターンを
  1例載せる（B3と同件）。
- **受け入れ基準。** protocol invalidを専用stepへ逃がすflowの回帰テスト。
  resume経路（記録されたrouteの再評価）でも同じ判定になること。

### A3. run dirの自動retention（opt-in）

- **問題。** `runs clean --older-than 30 --keep 5` は実装済みだが手動起動のみ。
  無人運用ではstuck/終了済みrunとprompt・全出力がディスクに溜まり続ける。
- **提案。** opt-inの保持ポリシー（置き場所は要設計: `defaults` はflowの性質
  ではないので、state root側の設定が筋が良い）。run開始時に既にruns rootへ
  触るフック（`protect_runs_root`, `src/engine.rs`）で機会的にprune。
  対象はterminal状態のrunのみ。未コミット作業を持つworkspaceに触らない
  既存cleanupの安全規則（`src/workspace.rs` `cleanup_keeps_everything_...`）
  をそのまま踏襲。live runの誤削除はnonce/pid判定でfail-closed。
- **受け入れ基準。** 設定なしで挙動不変。live run・unfinished workspaceが
  絶対に消えないことのテスト。

### A4. `max_cost_usd` の空振り警告

- **問題。** codex / agy / cursor は `Coverage::TokensOnly`（`src/preset.rs`）
  で **USDを一切計上しない**。これらだけで構成されたflowに `max_cost_usd` を
  書くと、ガードは常に素通りだが作者には守られているように見える。
  同梱ponytail 20本もcodexを多用している。
- **提案。** `validate`（無条件かstrictかは実装時判断）と `preflight` で、
  `max_cost_usd` 宣言 × 全ツールTokensOnly の組み合わせを警告し、
  `wall_clock_sec` 併用を促す。
- **受け入れ基準。** 該当flowで警告、Coverage::Costのツールが1つでも
  入れば沈黙。

## B. skills / guide への追記（知識で直す）

エンジン変更なしで今日から効く定石が3つ、どの文書にも書かれていない。

- **B1. run dir隔離。** writerを含むflowはworktreeモード（エージェントの
  cwdがworktreeになり、run dirは呼び出し側cwdに残る）にするか
  `--runs-dir` をツリー外へ。既定の `workspace.mode: current` +
  `access: write` では、routeが読む証拠（stderrファイル、log.jsonl）に
  被判定プロセス自身の書き込みが届く（`docs/v1-backlog.md` の
  accepted boundary #2 と整合する運用側の緩和策）。
  → `sfh-context-workspace`、`sfh-flow-review` のチェックリスト。
- **B2. ビルドキャッシュ共有。** worktreeモードはrunごとにキャッシュが
  コールド。`defaults.env: {CARGO_TARGET_DIR: ...}` や sccache、共有npm
  cacheで吸収できる（`env:` は既にfirst-class）。Rust/Nodeの実例を
  ponytailのprofile例か `sfh-context-workspace` に。
- **B3. 救済（salvage）パターン。** 失敗stepの生出力は捨てられず
  `outputs` にバナー付きで残る事実と、`on_error: goto:salvage` で
  再解釈させる書き方。A2実装後は `when_protocol_is` 版に更新。
  → `sfh-failure-recovery`。
- **B4. コスト計上範囲の明記。** どのツールがUSD非計上か（A4と同件）を
  `sfh-flow-design` の予算節と `guide` に1行ずつ。guideは110行予算
  （`src/main.rs` `guide_fits_one_screen`）に収めること。

## C. リポジトリ衛生

- **C1. mainの遅れ。** `main` はPR #16（v1.4相当）で止まり、#17–#20
  （v1.5.0 / v1.5.1 / zombie修正）は作業ブランチにしかない。この
  backlogを載せるPRのマージで解消される。
- **C2. CHANGELOGの言語方針。** READMEは英語首位、CHANGELOG v1.5.xは
  日本語。対象読者をどちらかに決めて明記する（どちらでもよいが、
  決まっていないのが問題）。
- **C3. skills評価の拡充（P2）。** `skills/evals/` は発動判定
  （trigger-cases.json）のみ。「このskillを読んだAIが書くflowは実際に
  改善するか」の成果評価が無い。ponytailのうち数本を実プロジェクトで
  完走させ、runログと修正をpackへ還流するのが先決で、その後の課題。
- **C4. docs-only変更でフルCIを走らせない。** CIは意図的に全ブランチ・
  全pushで全ジョブ（3OS build/test + install検証×3）を回す。v1.0.0の
  教訓（mainしか走らずコンパイル不能バイナリを出荷）による設計だが、
  README/CHANGELOG/`docs/` だけの変更にも同じフルセットが回るのは浪費。
  - **前提。** このrepoでは「ドキュメント」の多くが検査対象である。
    不活性（CIの何も読まない）なのは root直下の散文 `*.md`（README*、
    CHANGELOG、CONTRIBUTING、SECURITY、SUPPORT、CODE_OF_CONDUCT、
    AGENTS.md、CLAUDE.md）、`docs/**`、LICENSE、`.github/ISSUE_TEMPLATE/**`、
    `.github/pull_request_template.md` のみ。`skills/**`（skills_checks.py
    がSKILL.md・catalog・参照fileを読む）、`examples/**`（validate/plan）、
    `src/guide.txt`、`schema/**`、`installers/**`、`tests/**`、
    `.github/workflows/**`、`Cargo.*`/`deny.toml`/`rust-toolchain.toml` は
    見た目が文書でも検査対象なので除外してはならない。
  - **提案。** workflowレベルの `paths-ignore` ではなく、冒頭に軽量な
    変更検出ジョブを置き、重いジョブへ `if:` 条件を付ける形を推奨。
    `paths-ignore` はworkflow自体を起動しないため、branch protectionの
    required checkが "Expected" のまま詰まる。`if:` でskipされたジョブは
    required check上はpass扱いなので保護設定と両立する。除外は上記の
    不活性パスの明示列挙とし、`**.md` の包括指定は使わない。
  - **受け入れ基準。** docs-onlyのpushで重いジョブがskipされ、それ以外を
    1 fileでも含むpushでは全ジョブが走る。v1.0.0の教訓コメントは残し、
    「このskipはビルドを壊せない変更に限る」という理由を追記する。

## E. AIユーザー実地レビューからの発見

sfhを「使う側のAI」を演じたレビュアー（Fableサブエージェント1体）に、
src/を読まずguide/help/README/schema/skills/machine-api.md/エラーメッセージ
だけを頼りに7エクササイズ（authoring、cmd-onlyフロー実行、機械IF、detach運用、
fail-closed体験、典型ミス13種、skills実効性）を完走させた結果。総合判定は
5段階中4「ソース読解ゼロで使いこなせる」。以下は実測で出た具体的欠陥。

### E1. run/wait エンベロープの `error.code` が失敗クラスを表さない（最重要）

- **問題。** guideは「Failures carry a stable error.code
  (SFH_PROTOCOL_INVALID, ...); branch on it」と約束するが、実測では
  run/waitの外側エンベロープでプロトコル失敗が汎用 `SFH_FLOW_INVALID`
  （本来「flow fileの静的検証失敗」）に、max_visits stuckが
  `SFH_REPLAY_REFUSED`（本来「replay policyが未完了effectの再実行拒否」）に
  丸められる。コード表（`src/machine.rs`）には `SFH_PROTOCOL_INVALID` /
  `SFH_TERMINAL_MISSING` が定義済みなのに外側に現れない。真の分類は
  `runs why --json` の `protocol_failure` / `last_position.via` まで
  読まないと取れない。**A2（`when_protocol_is:`）と同根**——route露出と
  エンベロープ露出を1つの作業として設計する。
- **提案。** run/waitのfail経路で実際の失敗クラスをエンベロープに載せる
  （stuckは専用コード、例 `SFH_STUCK` の新設を含め検討）。安定語彙の
  変更になるので `machine::SCHEMA_VERSION` の扱いを含めて設計する。
  破壊的変更が重いなら、最低限guideの「branch on it」を「run/waitの
  error.codeは粗い。分類は `runs why --json` を読め」に1行修正する。
- **受け入れ基準。** プロトコル失敗runとmax_visits stuck runで、
  `--json` エンベロープの `error.code` が意味表と一致する回帰テスト。

### E2. `sfh run --json`（usage error）が空stdoutを返す

- **問題。** flow引数なしの `sfh run --json` はstdout空・stderrにusage・
  exit 2。`docs/machine-api.md` 自身が「configuration or usage errorも
  エンベロープで返す」「機械callerが最も必要とするケース」と書いている
  約束の違反。他コマンドのusage errorも同様か横断確認が要る。
- **提案。** 引数解析段階のusage errorでも `--json` 時はエンベロープを
  stdoutへ出す（`SFH_USAGE`）。小規模。
- **受け入れ基準。** `sfh run --json`（引数不足）でstdoutが有効な
  エンベロープ・`error.code: SFH_USAGE` になる回帰テスト。

### E3. strictメッセージが第一選択の修正を示さない（B群と併せて）

- **問題。** ①cmd stepの「effects: unknown + replay.rerun」strict issueは
  `replay.unfinished: stuck/fail` だけを提案するが、読み取り専用stepの
  正解は `effects: read` 宣言。メッセージ通りだと次善手に誘導される。
  ②`workspace.mode: auto` の解決通知がstrict issue（exit 2）扱いで、
  解消方法が書かれていない。レビュアーは推測で `mode: git-worktree` に
  して解消した。
- **提案。** ①メッセージに「If the step is read-only, declare
  `effects: read` instead.」を追記。②autoのstrict issueに「Declare
  `mode: git-worktree` explicitly to accept this.」を追記（または解決通知を
  issueに格上げしない）。どちらも `src/flow.rs` の
  `strict_warnings` 近辺。
- **受け入れ基準。** 両メッセージが対処法を含むことのテスト（文字列固定）。

### E4. skill同梱skeletonがskill自身の `validate --strict` を通らない

- **問題。** `sfh-flow-design` はwriterに `workspace.mode: auto` を推奨し
  （手順）、かつ手順5で `validate --strict` を課すが、autoはE3②により
  strictでexit 2。**skill同梱のskeleton自体がstrictを通らない**（実測）。
  加えて手順7の `sfh plan FLOW --json --save` は `--save` に
  ディレクトリか `--state-dir` が要り、記載のままではエラー。
- **提案。** B群（skills追記）の一部として、①E3②の解消後にskeletonを
  strictクリーンにする、②手順7を
  `sfh plan FLOW --json --save --state-dir <dir>` に修正、③手順4の
  linterパスがskillディレクトリ相対な点に絶対パス解決の注記。
- **受け入れ基準。** `skills/sfh-*/assets/*.yaml` が
  `validate --strict` クリーン（現状のCIは素の `validate` のみ）。
  strictをCIに足すかは実装時判断。

### E5. 軽微（P3、まとめて1コミット）

- 人間向け `runs why` にstuck/failの機械的理由（`via: max_visits` は既に
  JSONにある）を出す。
- プロトコル診断のstderr行が2重表示される。
- `retry_on: any` でも「transient failure, retrying」と表示する
  （anyは意味的失敗も拾うのに"transient"と呼ぶ）。
- routeにスカラを書いた時のserde型エラーに正しい形 `- {goto: <step>}` を
  添える。
- guideにrouteの `{goto: fix}`（スペース必須）の罠を1行明記
  （`on_error: goto:fix` のコロン詰めと非対称で誤推定しやすい。guideは
  110行予算内で）。

## F. 10並列エージェント実地レビューからの発見

Sonnetサブエージェント10体（実務シナリオ5・敵対テスト4・文書検証1）に
それぞれ独立タスクを与えた結果。**F1–F3は本セッションで再現確認済みの実バグ**。
F4以降は報告のみで未再現、または既知境界との差分。

### F1. validate の計算量が step 数に対してほぼ O(n²)（再現確認済み）

- **実測（debug build）。** 500 step=0.08s / 1000=0.30s / 2000=1.13s /
  4000=3.86s。倍増ごとに約3.8倍で、明確な2乗。報告者は2万stepで
  RSS 3GB超・サンドボックスにKILLされた。**敵対的入力ではなく、
  ごく普通の直列flow**（サイクルも並列も無し）で踏む。
- 別系統として、未知フィールド配下の深いネストYAML（数百KBで5万段=40秒、
  20万段は60秒超CPU張り付き）も同じく2乗。こちらは敵対的入力。
- **提案。** validate内の step 走査（おそらく id 解決や到達性・支配解析で
  線形探索を step ごとに回している）をmap索引化する。まず profiling で
  2乗の源を特定すること。**注意: 上記はdebug buildの実測**で、releaseでは
  数倍速いはずだが漸近計算量は変わらない。
- **受け入れ基準。** 2000 step の validate が線形時間の範囲に収まること
  （回帰テストは時間ではなく「n倍のstepでm倍以内」の比で書く）。

### F2. `status`/`wait`/`stop` のフラグ順序依存（再現確認済み）

- **実測。** `sfh status --runs-dir A --state-dir B` は B を見て
  「no runs found」、`sfh status --state-dir B --runs-dir A` は A を見て
  正しく報告する。**後に書いた方が勝つ**。READMEは「`--runs-dir` が
  run artifacts の所在では `--state-dir` に勝つ」と明言しており、`run` は
  実際にそうなっている（`StateRoot::resolve(state_dir, runs_dir)` が
  runs_dir 優先）。`cmd_watch`（`src/main.rs`）だけが両フラグを同じ
  `runs_dir` 変数へ順に上書きしているため、`run` と挙動が食い違う。
- helpの記載順（`--runs-dir` → `--state-dir`）どおりに並べると負ける方に
  なるため、**helpに従った利用者が壊れる**のが特に悪い。
- **提案。** `cmd_watch` も `run` と同じく両方を収集して
  `StateRoot::resolve` に委ねる。小規模。
- **受け入れ基準。** 両順序で同じ run を解決する回帰テスト。

### F3. live run に対する `--resume` / 同一 run-dir への並行実行が無防備（再現確認済み）

- **実測①。** 実行中のrunに `sfh run --resume <その run dir>` すると、
  **拒否されず**もう一度同じstepを起動し、生きている元プロセスと並行して
  同じ run dir に書く。両方 exit 0。
- **実測②。** 2つの `sfh run --run-dir <同一>` も同様に両方受理され、
  step が2回実行され `log.jsonl` に step_start が2件並ぶ。最終 `status` は
  矛盾を検出せず「done」と報告。
- **文脈。** nonce・pid・pid_start による所有権判定は `watch.rs`
  （status/wait/stop）と `--carry-budget-from`（`carry_source_is_final`）
  には実装済みなのに、**run開始側にはliveness確認が無い**。`--run-dir` は
  helpが「advanced; choose a new/empty path」と警告しているが、`--resume` /
  `--resume-latest` は日常操作で、「AIオーケストレータが止まったと誤判断して
  resumeする」はまさに想定運用で起きる。
- **緩和されている面。** `effects: external` + `replay.unfinished: stuck`
  を宣言したstepは、この経路でも replay ガードが再実行を拒否する
  （a03が kill -9 実証で確認）。危険なのは宣言のないstep。
- **提案。** run開始時（fresh・resume・`--run-dir` 指定のすべて）に対象
  run dir の nonce を読み、所有プロセスが生存していれば拒否
  （`SFH_WORKSPACE_BUSY` の同系統か新コード）。`--adopt-workspace` の
  ような明示的な上書き手段を用意するかは実装時判断。
- **受け入れ基準。** 生存runへのresumeと同一run-dirへの二重起動が
  fail-closedで拒否される回帰テスト（`watch.rs` の
  `owner_verifiably_dead` を再利用できるはず）。

### F4. 監視系コマンドだけが status.json の改ざんを信じる（未再現・要判断）

- **報告。** killしたrunの `status.json` の `state` を `"done"` に書き換えると
  `status`/`wait`/`runs show` は log.jsonl と突き合わせず ok:true を返す。
  一方 `run --resume` と `runs why` は log.jsonl を正とし未完了を検出する。
- **判断が要る点。** `docs/v1-backlog.md` の accepted boundary #2
  「run directoryを変更できるユーザーは履歴も変更できる」の範囲内であり、
  **新規の脆弱性ではない**。ただし「同じrunについて監視系と実行系が
  違う答えを出す」非対称性は、boundaryの記述が想定していない挙動なので、
  boundaryの文言を更新するか、監視系にクロスチェックを足すかを決める。
- 同系統: a05が「meta.json / log.jsonl / execution-closure.json を一貫して
  偽造すれば `--force-resume` なしにflow変更を通せる」と報告。これも
  boundary #2そのもの。**a05の17件の攻撃のうち、パストラバーサル・symlink・
  tainted var・access昇格はすべて突破できておらず堅牢だった。**

### F5. 到達可能だが終端に絶対届かないflowを誰も警告しない

- 自己ループ、終端の無いgoto循環、即stuckするだけのflowは `--strict` でも
  素通り。到達不能step検出はあるのに「到達可能だが end/fail に届かない」
  判定が無い。A系の静的検査強化として `strict_warnings` に追加できる。
- 関連（a08の初見AI体験）: **`route:` を省略した成功パスが、意図せず
  次のAI/writeステップへ落ちる**のは文法エラーにならず、`sfh graph` を
  自発的に叩かないと気づけない。M3（catch-all無し）の警告はあるので、
  「成功パスがwriter/AI stepへ暗黙fall-throughする」ケースの警告を検討。

### F6. 予算・ループガードの穴（a10、16ケース実測）

- **retryのbackoffが budget_reserve 窓より粗いと budget landing を完全に
  スキップ**し、`wall_clock_sec` 超過の生Errで即死する。着地判定がstep間
  にしかないため。reserve をbackoffより大きく取れという運用注意を
  guide/skillsに書くか、retry待機中にも着地判定を入れる。
- **retryの試行回数が `max_total_steps` にカウントされない**。
  `max_total_steps=1` でも初回+8リトライ=9プロセスが走る。仕様として
  正しい（leaf run単位の上限）としても、可視性ギャップなので
  `runs show` などに試行回数を出すか、文書で明示する。
- それ以外（max_total_steps境界、max_visits+on_max_visits、通常の budget
  landing、foreach 100/101件、max_parallel実測ピーク=設定値ちょうど、
  retry回数とbackoff倍加、budget_reserve=0のvalidate拒否）は**すべて
  宣言どおり正確**で、暴走・ホスト危険事象はゼロ。

### F7. 機械インターフェースの追加事例（E1/E2の補強）

- `sfh status --json` は stuck 到達時のみ `error` が**オブジェクトでなく
  生文字列**になる型不整合（machine-api.mdは object|null と規定）。E1に統合。
- `sfh runs why <存在しないdir> --json` も stdout 空 + stderr 散文。E2の
  範囲が `run` だけでないことの実例。`--json --verbose` 併用エラーも同様。
- `preflight --json` の `ok` が「バイナリ未インストール（環境要因）」と
  「flow自体の静的誤り」を区別しないため機械判定しにくい。

### F8. ドキュメントの実行可能性（a07）

- **README Quick Start が案内する `sfh validate flow.yaml --strict` を、
  直前に載っているそのYAML例に対して実行すると exit 2**。`sfh guide` の
  5例も同様。E3/E4（strictとautoの衝突）と同根の可能性が高く、
  E3の修正で解消するか要確認。解消しないなら、READMEとguideの例を
  strictクリーンにするか、案内するコマンドを素の `validate` にする。
- `contexts.file:` に動的パス（`{{run_dir}}` 等）が使えるかguide/schemaに
  記載が無く、AIが確証を持てず代替設計に逃げた（a01）。1行明記する。
- `context:` 未宣言のstepが `{{context_file}}` を参照すると黙って空文字列に
  解決される（a02）。strictで検知する候補。

### F9. macOSでは `sfh stop` がzombieを生存と誤認する

- **問題。** `pid_is_zombie` はLinuxが `/proc/<pid>/stat` の状態文字を読むのに
  対し、macOSを含むそれ以外のUnixは常に `false`（「判断できない」）を返す
  （`src/execute.rs`、既知の制限としてdoc commentに明記済み）。そのため
  `pid_alive` がzombieを生存と答え、`kill_pid_tree` は5秒+3秒のpoll窓を
  使い切ったうえで **実際には殺したprocessを「殺せなかった」と報告** し、
  `sfh stop` が exit 1 を返す。
- **踏む条件。** runのparentがzombieを刈り取らない場合。`--detach` した
  runのparentはinitなので即座に刈られ、通常は踏まない。踏むのは
  「runを子processとして起動し、waitせずに `sfh stop` を呼ぶ」呼び出し側
  ——**まさにAIオーケストレータがsubprocessでsfhを起動して監視する形**。
  F3の回帰テスト `tests/run_ownership.rs` がこの形だったためCIで表面化した
  （testはteardownをkillへ変更して回避済み。gap自体は未修正）。
- **提案。** macOSの `pid_is_zombie` を実装する（`sysctl` の
  `KERN_PROC_PID` で `kinfo_proc.kp_proc.p_stat == SZOMB` を見る、または
  `proc_pidinfo`）。Linux実装と同じく「読めなければfalse」を守ること。
- **受け入れ基準。** macOSで、刈り取られていない子processに対する
  `sfh stop` が成功を返すこと。CIのmacOS runnerで検証できる。

> 10体の生レポートはレビュー時の作業ディレクトリに残置（repoには入れない）。
> 実務シナリオ5本（CI復旧・並列調査合議・DB migration runbook・初見AI体験・
> --json駆動ドライバ）はいずれも**src/を読まずに完走**しており、
> Fableレビューの総合判定4/5を裏づけている。特にa03は apply 実行中の

> （sfhの中核的な安全主張の実地証明）。

## D. 検討して「直さない」と決めたこと（再訪時の判断材料）

- **stuckの処置の自動化はしない。** stuckは「sfhが安全に決められない
  判断を人間へ返す」機能そのもの。改善するなら「気づきやすさ」
  （`runs list --json` を状態でフィルタする監視ラッパー）まで。
- **step間prompt injectionのエンジン強制はしない。** `{{steps.x.output}}`
  は生テキストで次のプロンプトへ入る。これはこのカテゴリ全体の未解決
  問題で、skillsのuntrusted-evidence定石（`sfh-flow-design`
  anti-patterns）が現実的な緩和。context bundleのタグ無害化は実装済み。
- **live-run改ざんの完全防御はしない。** OSサンドボックスの仕事
  （accepted boundary #1, #2）。B1の運用定石で実務上のリスクを下げる。
- **認証・レート制限・シークレット管理は運用。** `doctor` の定期実行、
  `tool_max_parallel`、secretはflow外で注入。first-classなsecret
  providerは需要が見えてから。

## 実装順序

**先頭は再現確認済みの実バグ3件（F2 → F3 → F1）。** F2は小規模、F3は
安全性に直結、F1はprofilingが要るので3番目。その後:

F2 → F3 → F1 → A1 → A2+E1+F7（同根なので一体で設計） → E2 → A3 → A4 →
E3+F8 → F5 → F6 →（engineが安定してから）B群+E4 → E5 → C2/C4。

A項・E項・F項は互いに独立なので、themed commitを分けてこの順に積む。
B群とE4はengineの変更内容が確定してから書かないと二度手間になる。
F4は「直すか、boundaryの文言を更新するか」の判断が先。
