## 0. 全機能共通の不変条件

1. **境界**: sfh は配管について判断し、仕事について判断しない。本仕様の全機能は
   「観測事実の記録・露出」か「ユーザーが YAML で宣言した分岐の実行」だけで構成する。
   LLM 呼び出し・スコアリング・自動停止判断を sfh に入れない。
2. **3 OS 同一挙動**。全 branch push と PR で Windows / Linux / macOS の
   build・Clippy・単体・挙動テストを必須にする。
3. **新規クレート禁止**。既存依存(serde_json / regex / libc / windows 系)のみ。
4. **log.jsonl は追記のみの後方互換**。既存キーの意味・型を変えない。新キー追加のみ。
   旧 sfh が新 log を読む必要はないが、新 sfh は旧 log を今までどおり読めること。
5. **flow.yaml の新キーは schema/flow.schema.json にも追加**。`Route` 等は `deny_unknown_fields` なので、
   旧 sfh は新キー入りフローを**大声で**拒否する(静かな誤動作なし)。これは仕様として許容。
6. **fail-closed**: 判定不能・データ欠落・0 件は常に「マッチしない / 拒否」側に倒す。
7. **resume に触る機能(F1, F3)は、挙動テストを実装より先に書く**。
8. exit code の追加は 4 のみ(run/status とも空きを確認済み: run 0/1/2、status 0/1/2/3、wait はフロー code か 3)。

### 実装順序(依存関係順)

```
T-0 スタブ CLI → F2 idle → F4 ログ拡充 → F3 stuck → F1 when_members
→ F6 when_exit → F5 on_budget → F7 ドキュメント                        = v1.1.0
→ F8〜F13 はトリガー成立順
```

- F2 は execute/leaf に閉じ独立。F4 は F1(票の記録)と F13(読み手)の土台。
- F3 は F5 の土台(着地連鎖の終端が `goto: stuck`)。
- F1 が最大で resume に触るため、土台が安定してから最後に。

### T-0(テスト基盤・B-15): セッション報告スタブ CLI

F1/F8/F11 の挙動テストに、セッション ID を報告する最小スタブが要る(`echo` はセッションを報告できず
F-11 の resume 検証で必ず落ちるため)。`claude -p --output-format json` 形の JSON を 1 行返す
小さな Rust テストバイナリ(3 OS で確実)を `tests/` 配下に置く。引数で
「最終行に出す文字列 / exit code / sleep 秒 / stderr に吐くか」を制御できること。

# Phase 1(v1.1)

## F1: `when_members` — fan-out 合議の決定論的集計

### 目的

「N 体の独立判定器の票を数えて分岐する」を sfh 本体の述語にする。現行の
`cmd: ["sh","-c","grep -c '^REVIEW-PASS$' ..."]`(examples/v1-harden-r4.yaml:692)は
(a) Windows で Git Bash 必須、(b) 本文中の単独行引用を票に数える、(c) そもそもグループの
route は最終メンバーの最終行しか見ない、という 3 点で壊れている。
さらに検証で判明した事実として、**route 判定テキスト(ヘッダ無し plain)には失敗メンバーの
生出力がそのまま入る**(src/engine.rs:2128 は `d.chain_output` を push し、`[sfh: FAILED]`
バナーは集約 `agg` 側にしか付かない)。したがって集計は文字列ではなく
**engine が保持する成否**で判定しなければならない。

### YAML

```yaml
- id: review
  max_parallel: 3
  parallel:
    - { id: rev_a, use: rev, on_error: continue, prompt: "...最終行に REVIEW-PASS か REVIEW-FAIL..." }
    - { id: rev_b, use: rev, on_error: continue, prompt: "..." }
    - { id: rev_c, use: rev, on_error: continue, prompt: "..." }
  route:
    - when_members: { last_line_is: "REVIEW-PASS", at_least: 3 }   # または all: true
      goto: wrap
    - goto: fix        # 数えられない出力・失敗・タイムアウトは全部こちら
```

`Route` 構造体(src/flow.rs:218)に追加:

```rust
pub when_members: Option<WhenMembers>,
// WhenMembers { last_line_is: String, at_least: Option<u32>, all: Option<bool> }  #[serde(deny_unknown_fields)]
```

### 意味論

- 対象: `parallel:` / `foreach:` を持つステップの route のみ。
- 各メンバーについて「票」と数える条件は次の **両方**:
  1. そのメンバーの `LeafDone::ok()` 相当(正規化 `exit == 0 && !timed_out && !interrupted`。src/leaf.rs:115)。
  2. メンバーの**個別 chain 出力(compact 前・plain に入るのと同じ生テキスト)**の最終非空行
     (`leaf::last_line`、trim 済み = CRLF 耐性は既存関数から継承)が、`last_line_is` の
     テンプレートレンダリング結果と**完全一致**。
- 母数: parallel は構成メンバー数、foreach は生成アイテム数。
- `at_least: N` → 票数 ≥ N。`all: true` → 票数 == 母数 **かつ 母数 ≥ 1**。
- **母数 0(foreach が 0 件)は常に不成立**(fail-closed。`all: true` の空集合真を禁止)。
- グループが hard_fail(`on_error: continue` の無いメンバー失敗)した場合は従来どおり
  route 自体が評価されない(on_error 経路)。合議イディオムではメンバーに
  `on_error: continue` を付けるのが正、と README に明記。
- fallback で走ったメンバーも id は不変なので同じ規則で数える。
- restored メンバー(resume 復元)は下記スナップショットの記録値で数える。

### 実装

- グループ集約ループ(src/engine.rs:2050 付近と foreach 側)で
  `MemberVerdict { id, ok, exit, last_line }` を収集。live は `LeafDone` から、
  restored はスナップショット(下記)から。
- `evaluate_route`(src/engine.rs:3169)のシグネチャに `members: Option<&[MemberVerdict]>` を追加。
  `when_members` 規則は `members == None`(leaf ステップ)なら不成立(validate で到達不能だが防御)。
- `last_line_is` は既存述語と同様にテンプレートレンダリングする。

### ログ(追記のみ)

- `aggregate_end`(parallel/foreach 共通イベント)に追加:
  `"members": [{"id": "...", "ok": true, "exit": 0, "last_line": "REVIEW-PASS"}, ...]`
  (`last_line` は 200 字で機械的に切る)。**このスナップショットが resume の唯一の情報源**。
- 規則がマッチした position イベントに `"votes": N, "voters": ["rev_a", ...]`(F4 と統合)。

### resume

- `PendingRoute`(src/engine.rs:318)に `members: Option<Vec<MemberVerdict>>` を追加し、
  `aggregate_end.members` から復元(現行の from_plain 復元経路 src/engine.rs:696-706 に追加)。
- pending route の再評価が `when_members` 規則に達し、`members` が欠落している場合
  (= v1.1 以前の run にフロー編集 + `--force-resume` で `when_members` を足した場合のみ発生):
  **明示エラーで拒否**。「黙って catch-all に落とす」は禁止(run の世代で routing が静かに変わるため)。
  エラーメッセージは「this run predates per-member route records; re-run the group step or remove when_members」。

### validate

- `parallel`/`foreach` の無いステップでの `when_members` → エラー。
- 同一規則内で他の述語(`when_contains` 等)との併用 → エラー(AND 意味論を作らない)。
- `at_least` と `all` の同時指定 / どちらも無し / `at_least: 0` → エラー。
- parallel で `at_least >` 構成メンバー数 → エラー(静的に判定できる)。
  foreach は母数が動的なので検査不能 — 実行時は永遠に不成立(fail-closed)、README に明記。

### テスト(engine_behaviour.sh 追加。resume 系を先に書く)

1. 3 メンバー全員一致 → `at_least: 3` でマッチ。
2. **バナーバグの決定打**: `on_error: continue` のメンバー 1 体が「一致する最終行を吐いて exit 1」
   (T-0 スタブ)→ 票に数えられず catch-all へ。
3. 本文中に単独行で needle を引用、最終行は別 → 数えない。
4. foreach 0 件 + `all: true` → 不成立。
5. グループ途中 kill → resume → スナップショット経由で live と同一の判定。
6. `members` 欠落 pending + `when_members` → 明示エラー。
7. validate の各エラー(leaf 使用 / 述語併用 / 量化子 0 個・2 個 / `at_least` 超過)。
8. CRLF(`\r` 付き最終行)でも一致。

### 受け入れ条件

v1-harden-r4 の `verdict` ステップを `when_members` に置換した派生フローが
validate + dry-run を通り、`sh` 依存の集計が消えること。

### 非スコープ

`contains`/regex のメンバー量化版は作らない(完全一致のみ。誤爆面を増やさない)。

## F2: idle 二時計 — 「経過時間」と「最終出力からの時間」

### 目的

B-12(112 分の無言ハング、全外部信号が「正常稼働中」)への対策。sfh は子の出力チャンクを
逐次観測しているのに(src/execute.rs:875 `spawn_reader`)、最終活動時刻を捨てている。
記録・露出・リトライ分類だけを入れ、**強制 kill(`stall_after_sec`)は入れない**(F12 へ分離)。

### 実装

1. `execute::run_cmd`: 開始時に `Arc<AtomicU64>`(開始からの最終活動 ms)を作り、
   **stdout / stderr 両方の** `spawn_reader`(src/execute.rs:795-796)に渡す。各 read チャンクで store。
   片方だけだと stderr にのみ進捗を出すツールが全部「ハング」に見える。
2. `ExecOutcome` / `LeafDone` に `idle_ms: u64`(終了/kill 時点の経過 − 最終活動)。
   一度も出力が無ければ idle_ms == 経過時間。
3. run レベル活動時計: engine が `Arc<AtomicU64>`(epoch 秒)を leaf 実行系へ渡し、
   どの子のチャンクでも touch。heartbeat スレッド(src/engine.rs:1658)が status.json に反映。
4. リトライ分類(src/leaf.rs:1263-1270): `RetryMode::Transient` を
   `(!timed_out && is_transient_failure(...)) || (timed_out && idle_ms >= hang_after_sec * 1000)` に。
   `hang_after_sec`: defaults / step で上書き、既定 300。
5. F8(await)実装後、await 待機は分類対象外(子プロセスが無いので自然にそうなる)。

### ログ / status.json(追記のみ)

- `step_end` に `"idle_ms": N`。
- status.json に `"step_started_utc"`, `"last_output_utc"`(未出力なら null), `"visit"`。
- `sfh status` 人間表示: `running  fix_f2 (visit 2)  41m elapsed, 38m since last output, $0.31`。
  旧 status.json(キー欠落)では新表示部を出さない(前方互換)。

### 既知の退化(README に表で明記)

最後に JSON を一塊で吐く preset(claude / grok / agy)では idle ≒ 経過時間となり、
ハング分類は「タイムアウトは常に 1 回リトライ」に退化する。ゼロ出力で死んだ試行の
1 リトライは損失ゼロなので許容。観測できるのはパイプの活動でありモデルの活動ではない。

### テスト

1. 「1 行吐いて永久 sleep」スタブ + 短い timeout + `retry_on: transient` + 小さい hang_after_sec
   → `.a2` リトライ痕跡がある。
2. 「毎秒出力し続ける」スタブ + timeout → リトライしない(超過であってハングではない)。
3. **stderr のみに出力**するスタブ → idle が更新され、ハング扱いされない。
4. `step_end` に `idle_ms` が出る。
5. sleep 中の status.json に `last_output_utc` / `step_started_utc` / `visit` が出る。

## F3: `stuck` — 第 3 の終端(exit 4)

### 目的

「作業は保存されているが、人間の判断なしに先へ進んではいけない」を機械可読にする。
現行は examples/v1-harden-r4.yaml:738 の `unresolved` が `goto: end` = exit 0 で、
非収束 run が成功と同じ顔をする。文字列規約(最終行 UNRESOLVED を呼び出し元が grep)は
v1 で潰してきた fail-open と同型なので禁止し、終端を追加する。
**判定は一切増えない** — ユーザーが `goto: stuck` と宣言した所に到達したときだけ。

### 仕様

- 予約 goto 先 `stuck` を `end` / `fail` と同格に受理: `route[].goto` /
  `on_error: goto:stuck` / `on_max_visits: goto:stuck`。
- engine 内部: フロー本体の戻りを `Result<FlowEnd, String>`、
  `FlowEnd = Completed | Stuck { after: String }` に。終了処理は既存 `finish` クロージャ
  (src/engine.rs:2609)に `("stuck", cost, 4, ...)` を渡す。`error` フィールドには
  `routed to stuck after '<step>'` を格納。
- exit code: `sfh run` = **4**。HELP の EXIT CODES 行(src/main.rs:69)を
  `0 = succeeded / 1 = failed / 2 = config error / 4 = stuck` に更新。
- emit: 失敗時と同じ「最良の出力」partial emit。`--no-partial-emit` を尊重。
- log: 通常の position イベント(`next: "stuck"`、via は rule/catch_all/on_error/max_visits)。
- watch.rs: `terminal()` に `"stuck"` を追加。`sfh status` の exit に 4 を追加
  (既存 0/1/2/3 と衝突しない)。`sfh wait` は status.json の `exit_code`(4)をそのまま返す。
  **nonce / 実行ファイル検査は failed と同じ扱いに含める**(偽 status の `state:"stuck"` を
  無検査で信用しない — 既存の fail-open 対策と同水準)。
- runs list / show: state `stuck` を表示。

### resume 意味論(本機能の要)

- stuck run は failed と同様に**再開可能**(completed 扱いにしない)。
- **route 経由の stuck**: 再開開始点 = stuck へ分岐したステップ(最後の position の `after`)。
  **pending route は復元しない**(記録済み判定を再生すれば同じテキストで必ず再 stuck するため)。
  当該ステップを再実行する(visit は +1 され、通常の max_visits 検査に服す)。
- **on_max_visits 経由の stuck**: 再開すると入場検査で即再 stuck。これは仕様
  (visit カウンタを黙ってリセットする方が嘘)。正規の道は「フローの max_visits を直して
  `--force-resume`」— README に明記。

### validate(破壊的変更)

step id `stuck`(大文字小文字無視 — id 重複検査と同じ規則)を予約語として拒否。
既存フローが割れる可能性があるが validate が大声で落ちる。**リリースノート筆頭に記載**。

### テスト

1. route → stuck: run exit 4 / status.json `state: stuck` / `sfh status` exit 4 / `sfh wait` exit 4。
2. `on_max_visits: goto:stuck`。
3. partial emit が出る / `--no-partial-emit` で出ない。
4. resume: 判定スタブの参照ファイルを直してから resume → 判定ステップが再実行され、今度は通る。
5. resume(max_visits 経由)→ 即再 stuck。
6. validate: `id: stuck` / `id: STUCK` を拒否。
7. 偽 status.json(`state: "stuck"`)を status/wait が無検査で信用しない。

## F4: ログ拡充 — routing の「なぜ」を機械可読に

### 仕様(すべて追記のみ)

- **position**(route 評価経由 = via が rule / catch_all のとき):
  - `"rule"`: マッチした規則の 0-based index。
  - `"route_line"`: 最終行系述語ならその最終行、全文系(`when_contains`/`when_matches`)なら
    route_text 先頭 200 字。catch-all でも最終行を記録。
  - `when_members` マッチ時は `"votes"`, `"voters"`(F1 参照)。
- **step_start**: `continue_from` / `fork_from` の解決結果
  `"session_parent": {"mode": "continue"|"fork", "step": ..., "tool": ..., "id": ...}`。
- **step_end**: `"os"`: `std::env::consts::OS`(2体目提案 5 のコード部分はこの 1 キーで完結)。
- `load_resume` は既知キーのみ読むため影響なし。`sfh runs why`(F13)はこれを土台にするが v1.1 では作らない。

### テスト

1. ルーティングのある run の log.jsonl に `rule` / `route_line` が現れる。
2. `step_end` に `os`。
3. 新形式 log の run を resume できる(後方互換の回帰テスト)。

# Phase 2(v1.1.0 に前倒し実装済み)

## F5: `on_budget` — 予算の崖を着地パスに

### YAML

```yaml
defaults:
  max_cost_usd: 60.0
  wall_clock_sec: 43200
  on_budget: goto:wrap                       # 未指定なら従来どおり即 Err
  budget_reserve: { cost_usd: 2.0, wall_clock_sec: 900 }   # 省略時 0
```

### 意味論

- 発火点: 既存の予算検査と同じループ先頭(src/engine.rs:1797-1811)。
  閾値 = `max − reserve`(コスト・時間の各軸独立)。いずれかの軸で閾値超過かつ未着地なら、
  Err ではなく `on_budget` の goto 先へ跳ぶ。
- **1 run に 1 回だけ**。着地後は従来検査(max 本体)がそのまま生きる:
  reserve も食い潰したら従来どおり Err(fail-closed 保存)。
- resume: log の `budget_landing` イベントから「着地済み」を復元(resume 越しの 2 回目着地を許さない)。
- テンプレート変数(全ステップで利用可):
  `{{budget.spent_usd}}` `{{budget.elapsed_sec}}`(常時)、
  `{{budget.remaining_usd}}` `{{budget.remaining_sec}}`(上限未設定なら文字列 `unlimited`)。
- log: `{"event":"budget_landing","trigger":"cost"|"wall_clock","spent_usd":...,"elapsed_sec":...}`。
  `runs show` に `budget_landed` を表示。

### validate / dry-run

- `on_budget` の goto 先の実在(`end`/`fail`/`stuck` も可)。
- `budget_reserve` があるのに `on_budget` が無い → エラー。
  `on_budget` があるのに `max_cost_usd` / `wall_clock_sec` が両方無い → エラー。
- dry-run に `budget landing: goto wrap (cost reserve $2.00, wall reserve 900s)` を印字
  (route: に現れない goto の可視化)。

### 既知の限界(README に明記)

- コストは**報告値のみ**。USD を報告しないツール構成ではコスト軸は発火しない
  — 信頼できるのは wall-clock 軸。
- 検査はステップ間のみ。走行中ステップの超過は止められない
  → reserve は「最長ステップ 1 本 + 着地連鎖の合計」以上を見込むこと(見積もり指針まで書いて完成)。
- 推奨イディオム: 着地連鎖の終端を `goto: stuck` にし、「未完了だが整理済み」を exit 4 で申告。

### テスト

着地後 reserve 超過で Err / resume で 2 度目の着地無し / validate 各種 / dry-run 表示。

## F6: `when_exit`(+ 任意で `when_stderr_matches`)

### 仕様

- `Route` に `when_exit: Option<i32>`。ステップ自身の**正規化 exit**(`StepOutput.exit`)との等値比較。
- 既存述語との AND 併用可(既存規則と同じ合成)。`when_members` とは併用不可(F1 の排他を維持)。
- live は集約後の outputs から、resume は復元済み outputs から読む —
  **step_end 由来で既に復元されるため追加の永続化なし**(live/resume 対称)。
- グループステップでは合成 exit(hard_fail ? 1 : 0)。README に明記。
- 主用途: `on_error: continue` な cmd ステップの「**正しい理由で落ちた**」ゲート
  (攻撃 fixture の検証で「別の理由の非ゼロ」を合格に数えた実害 3 件への対処)。
  AI ステップでは exit にセッション検証等が畳み込まれる旨を README に明記(validate 警告は出さない)。

```yaml
- id: probe
  cmd: ["sfh", "run", "attack-fixture.yaml", "-q"]
  on_error: continue
  route:
    - { when_exit: 0, goto: broken }          # 攻撃が通った = ガード消失
    - { when_stderr_matches: "refusing to resume|no recorded access level", goto: guard_fired }
    - { goto: broken }                        # 別の理由で落ちた = 検証不成立
```

### `when_stderr_matches`(v1.1.0 で実装済み)

- `<id>.err.txt`(クリーン済み stderr)への regex。live/resume とも `read_contained` で
  **ファイルを読む**(対称性のため live もメモリではなくファイルを読む)。読取り上限 4 MB。
- ファイル欠落(手で消された resume 等)→ 不成立(fail-closed)。

### テスト

exit 3 の cmd + `when_exit: 3` → goto / probe パターン(when_exit: 0 で「通ってしまった」検出)/
resume 再評価の一致 / stderr 上のメッセージ照合と欠落時不成立。

# Phase 3(各機能の着手はトリガー成立後)

## F8: `await:` + `sfh answer` — 待機の一級化

**着手トリガー**: 人間ゲート(または親エージェントへの逆質問)を使うフローが 2 本以上実運用に入ったら。

- ステップ形: `await: { question: <template> }`。`tool`/`cmd`/`parallel`/`foreach` と排他(validate)。
  **`timeout_sec` 必須**(無期限の waiting は B-12 型の無言と区別不能になるため validate エラー)。
  期限切れの方針は従来どおり `on_error`。
- 実行: `<id>.question.txt` を書き、status を
  `{"state":"waiting","current_step":...,"question_file":...}` に遷移。
  `<run-dir>/answers/<id>.txt`(visit>1 は `<id>.v<n>.txt`)を 1 秒間隔でポーリング。
  **非空・通常ファイル(symlink 拒否・nofollow)・1 MB 上限**を読んだら、その内容を
  chain output として続行 — 既存の route / notes / テンプレートが全部そのまま効く。
- `sfh answer <run-dir> [--step id] <text | --file f>`: status が waiting かつステップ一致のときのみ
  書き込む(`--force` で無視可)。封じ込め検査 + 0600。ファイルを直接作ってもよい。
- status: **exit code は 3(running)のまま**、state 文字列 `waiting` で区別
  (既存ポーラーを壊さない)。表示は `waiting (approve): question at <path>`。
- heartbeat 継続。ハング分類(F2)の対象外。dry-run に `waits for answers/<id>.txt` を印字。
- テスト: waiting 遷移 / `sfh answer` で続行 / 期限切れ → on_error / symlink・空ファイル拒否 /
  回答内容に route が効く。

## F9: `prev_output` — 周回間比較の材料

**着手トリガー**: 成果物ベースの収束ゲート(`git diff --stat` 等)で足りない実例が出たら。

- `{{steps.ID.prev_output}}` / `{{steps.ID.prev_output_file}}`: 同一ステップの**直前 visit** の
  chain 出力。visit 1 では空文字列 / 空パス。レンダリング時にファイルから封じ込め読取り
  (RAM に 2 世代持たない)。resume は visits + 命名規則(`<id>.v<n>.chain.txt`)から再構成。
- README に注意: 散文差分での収束判定は言い換えに敗れる。第一選択は成果物への判定。

## F10: JSON 3 点セット

**着手トリガー**: 多フィールド判定(verdict + severity + 対象など)が必要なフローが実際に書かれたら。

- `expect: json`(ステップキー): chain 出力(compact 前)が JSON としてパース不能なら
  ステップ失敗扱い(`on_error` が効く)。`compact` との併用は validate エラー(要約が JSON を壊す)。
- フィルタ `| json:<RFC6901>`: `serde_json::Value::pointer` で抽出。パース不能・ポインタ不在は
  レンダリングエラー = ステップ失敗(fail-closed)。
- `when_json: { at: "/verdict", is: "OK" }`: `split: json` と同じ寛容抽出(フェンス・前置き許容)
  → ポインタ → 文字列等値。あらゆる失敗は不成立。
- `| fenced:json`(任意): 最後の ```json フェンスの中身を機械抽出。
- README: **単発 verdict には最終行方式を推奨し続ける**(出力切断時、JSON は壊れ、最終行は
  判定不能側に倒れる)。本機能は多フィールド・多件のハンドオフ専用。

## F11: `--import-session` — run をまたぐセッション復元

**着手トリガー**: 「前 run の温かいセッションを次のフローで使いたい」が実運用で繰り返し
(目安: 月 1 回以上)起きたら。**本機能は信頼境界を広げる。安易に前倒ししない。**

- CLI: `--import-session name=<run-dir>:<step-id>`(複数可)。フロー側は
  `continue_from: name` / `fork_from: name` で参照(ステップ id と名前が衝突したら validate エラー)。
- 読取り: 対象 run の log.jsonl から session(tool/id/cwd/marker/access)を封じ込め読取り
  (既存 read_contained 系を再利用)。
- 信頼規則(`--force-resume` の降格則と同型): 対象 run の meta.json が指すフローの
  fingerprint を再計算・照合できた場合のみ記録 access を採用。それ以外は unknown →
  read 以外は `allow_access_override: true` 必須。
- cwd スコープ検証(claude/grok/pi は同 cwd、cursor は store.db 実在)と marker 検証(F-11 機構)を再利用。
- README: プロバイダ側のセッション失効は sfh から観測できない場合がある(fork 失敗は検知可)。
- テスト: T-0 スタブで配管一式 / fingerprint 不一致時の access 降格 / 封じ込め違反の拒否。

## F12: `stall_after_sec` — 無出力の強制打ち切り(既定 off)

**着手トリガー**: 「status ポーリング + `sfh stop` による呼び出し元キル」で足りない実例が出たら。

- step / defaults の `stall_after_sec: N`(既定 off)。idle ≥ N でプロセスツリーを kill し、
  `timed_out` ではなく `stalled: true` として記録 → 定義上 transient なのでリトライ対象。
- `await` ステップと「沈黙して待つ」cmd 人間ゲートに適用してはならない旨を README に警告。

## F13: `sfh runs why` — 因果列の読み手

**v1.1.2**: 最終 durable event、最後の position、未完了 leaf/fan-out、
resume で再実行される対象を text/JSON で説明する最小診断版を実装済み。

**詳細traceの着手トリガー**: 最小診断版では不足する実運用例が明確になったら。

- 将来の詳細版 `sfh runs why <run-dir> [--json]`: log.jsonl **のみ**から、visit ごとの因果列
  (step / exit / tokens / cost / retry と transient 判定 / fallback 遷移 / compact 発火 /
  どの規則がどの行で発火してどこへ跳んだか / セッション親子)を出す。読取りは封じ込め。
- 用途: 差し戻しループの修正役へ `{{steps.trace.output | truncate:8000}}` として渡す機械可読履歴。
